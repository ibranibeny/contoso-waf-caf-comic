Rush hour: edge cache, cache-aside, autoscale

  1. Shoppers ask for product images. The Front Door edge has a cached copy: served from the edge, no trip to the origin.
  2. Not cached yet? The edge forwards the request to the origin, App Service, and caches the response (GET requests only).
  3. Product data: the app checks Azure Managed Redis first. Cache hit: a fast answer.
  4. Cache miss: read SQL Database, add the item to the cache, return it. That's the Cache-Aside pattern.
  5. CPU above 70%: Azure Monitor autoscale adds an instance, never above the maximum you set.
  6. The sale ends and CPU drops below 40%: autoscale removes the extra instance to save cost.

✎ CPU thresholds follow the example on Learn's autoscale overview (add above 70%, remove below 40%).

Sources on Microsoft Learn: Caching with Azure Front Door (updated 2026-07-15) · Cache-Aside pattern · What is Azure Managed Redis? (updated 2026-08-18) · Overview of autoscale in Azure Monitor (updated 2026-08-10)

Checkpoint: With the Cache-Aside pattern, what does the app do on a cache miss?
  • Return an error and retry later
  • Read the data store, add the item to the cache, then return it
  • Scale out the cache automatically

Answer: Read the data store, add the item to the cache, then return it. Cache-Aside loads data into the cache on demand: on a miss, read from the store, then populate the cache.
